# 正規表現エンジンとは

[前の章](./01-why-functional.md)では，悪役と，それを打ち倒す忘れられたアイデアを予告しました．この章でその両方を紹介して，最後に本書の残りのロードマップを示します．

## 文字列の集合を表す小さな言語

俗説をはぎ取ってしまえば，正規表現はとても小さなものです．ざっくり言うと，文字列の集合を記述するための記法です．

パターン`abc`は，文字列`"abc"`ただ1つを要素とする集合を記述します．パターン`a|b`は`"a"`と`"b"`の2要素からなる集合を記述します．そしてパターン`a*`が記述するのは無限集合で，`""`，`"a"`，`"aa"`，`"aaa"`とどこまでも続きます．

正規表現構文の演算子はどれも，小さな集合から大きな集合を組み立てる方法です．連接は端と端をつなぎ，`|`は合併を取り，`*`は繰り返します．(ちなみに，名前の由来は1950年代のStephen Kleeneによる「正規事象(regular events)」の研究にさかのぼります．`*`は彼にちなんでクリーネスターと呼ばれます．正規表現は，ツールチェーンにあるほとんどのものより年上ということです．)

「この文字列はこのパターンにマッチする?」という質問は，実際には「この文字列は，このパターンが記述する集合の要素?」という質問です．これが正規表現エンジンの職務内容のすべてです．パターンと文字列を受け取って，帰属についての質問にひとつ答える．

パターンは記述であり，マッチングはその記述への帰属チェックである．この見方は哲学的な言葉遊びに聞こえるかもしれませんが，実は本書のエンジニアリング上の心臓部です．記述とはただのデータですし，関数型言語において，データ構造の上の関数は日常業務そのものです．この考えはぜひ覚えておいてください．

## エンジンの3つの系統

帰属の判定はいろいろな方法で実装でき，世に存在するほぼすべての正規表現エンジンは3つの系統のどれかに属します．

**バックトラッキングエンジン**は，普段ほぼ間違いなく使っているものです．Pythonの`re`，JavaScriptの`RegExp`，Javaの`java.util.regex`，Ruby，Perl，PCREなどです．これらはパターンを小さなプログラムとして扱い，再帰的に実行します．この選択肢を試して，後続のマッチが失敗したら戻ってきてもう一方を試す，という感じです．バックトラッキングは実装が簡単で，後方参照のような非正規の機能にも自然に拡張でき，たいていは高速です．たいていは，ですが．この失敗モードが次の節の主題です．

**オートマトンエンジン**は，マッチングの前にパターンを有限状態機械へコンパイルします．事前にやるのがDFA，その場でやるのがNFAシミュレーションです．GoogleのRE2とRustの`regex`クレートが有名どころです．これらは線形時間のマッチングを保証していて，どんな入力でも爆発させられません．それこそが存在理由で，RE2は信頼できないユーザーからの正規表現をGoogleが受け付けられるように，まさにそのために作られました．

オートマトン方式の代償は，コンパイルフェーズと，それなりのエンジニアリング的複雑さを伴う状態機械の構築，そして後方参照をあきらめることです．(このトレードは割に合うと業界も少しずつ認めつつあります．たとえば.NETは現在，従来のエンジンと並べてオプトインの非バックトラッキングモードを出荷しています．)

**微分エンジン**が，ほとんど知られていない第3の系統で，本書の選択です．状態機械へのコンパイルなし，バックトラッキングなし．パターンそのものがデータ構造として1文字ずつ変換されていき，最後に答えが転がり出てきます．オートマトン系と同じ線形時間の保証を持ちながら，上から下まで木の上のひと握りの再帰関数のままでいられます．

このアイデアは1964年に生まれ，40年間文献の中で眠り，関数型プログラマたちの手で掘り起こされました．2009年の論文(その名も「Regular-expression derivatives re-examined」)は，関数型言語ではこの技法が実用的であるどころか快適であることを示しました．本書がたどり直すのはこの再発見です．アイデアそのものにはすぐ後でちゃんと対面します．

## 悪役:壊滅的バックトラッキング

まずは，主流の設計が破綻する様子を見てみましょう．次のパターンを考えます(構文`a?`は「`a`が1個，または何もなし」，`{3}`は「3回」の意味です)．

```
(a?){3}a{3}
```

書き下せば`a?a?a?aaa`です．これを入力`"aaa"`にマッチさせてみます．

バックトラッキングエンジンは左から右へ動作し，各`a?`は選択点(choice point)になります．貪欲に`a`を1個消費しようとしつつ，その場所を覚えておく．後で何かが失敗したら，ここに戻ってきて今度は何も消費しない方を試すためです．エンジンの記憶は，まるごとこの「リトライすべき場所」のスタックです．動きを追ってみましょう．

```
attempt 1: a? a? a? each eat one 'a'   -> "aaa" consumed, a{3} needs 3 more -> FAIL
attempt 2: first two eat, third skips  -> "aa" consumed,  a{3} needs 3, 1 left -> FAIL
attempt 3: 1st and 3rd eat, 2nd skips  -> "aa" consumed,  1 left  -> FAIL
attempt 4: only the first eats         -> "a" consumed,   2 left  -> FAIL
attempt 5: 2nd and 3rd eat, 1st skips  -> "aa" consumed,  1 left  -> FAIL
attempt 6: only the second eats        -> "a" consumed,   2 left  -> FAIL
attempt 7: only the third eats         -> "a" consumed,   2 left  -> FAIL
attempt 8: all three skip              -> "" consumed,    3 left  -> MATCH
```

独立した二択が3つあるので，エンジンは最大2 × 2 × 2 = 8通りの組み合わせを探索します．しかも成功する組み合わせは探索順の一番最後です．何を繰り返しやり直しているかにも注目してください．試行2，3，5はどれも`a`を2個消費して同じ理由で失敗しますが，エンジンにはそれらが同じ状況だと気づく手段がありません．覚えているのはリトライする場所であって，学んだ内容ではないのです．

では一般化します．`(a?){n}a{n}`をn個の`a`からなる文字列にマッチさせると，エンジンは2^n通りの組み合わせに直面します．n = 10なら千通りで，誰も気づきません．n = 20なら百万通りで，リクエストが遅くなります．n = 30なら十億通りで，リクエストハンドラはもはや暖房器具です．入力は大きい必要すらなく(たった30文字です!)，ただ形が悪ければ十分でした．

これが壊滅的バックトラッキングです．そして肝心なことに，パターンの見た目は完全に無害です．`(a?){30}a{30}`をわざわざ書く人はいませんが，繰り返しが入れ子になったり隣り合ったりする現実のパターン(たとえば`(\s*.*)+`)は，同じ爆発的構造を隠し持っています．こういうパターンはコードレビューをすり抜けます．誰かが試そうと思いついた入力では，どれも完璧に動いてしまうからです．

指数の崖が現れるのは，ちょうど悪い形をした入力に対してだけです．つまり，攻撃者が送ってくる入力に対してだけ，ということです．これを意図的に悪用する行為には名前が付いています．ReDoS，正規表現サービス拒否攻撃(regular expression denial of service)です．

## 2つの有名な障害

実際の事件は，どんな理屈よりも雄弁です．

2016年7月，Stack Overflowは30分あまりダウンしました．引き金は行末の空白を取り除く正規表現で，これがおよそ2万個の連続した空白文字を含む投稿に適用されました．このたった1つの文字列に対するバックトラッキングは約2億回の文字比較に相当し(二次関数的で，指数的ですらありませんが，それで十分でした)，レンダリング経路のCPUを張り付かせました．ヘルスチェックがタイムアウトし，ロードバランサがサイトをローテーションから外した，という顛末です．

2019年7月には，ウェブ全体の無視できない割合を担うCloudflareが，約30分にわたって全世界で502エラーを返しました．新しくデプロイされたWAF(ウェブアプリケーションファイアウォール)のルールに，核心部が`.*.*=.*`に相当する正規表現が含まれていたのです．特定の入力でこれが壊滅的にバックトラックし，すべてのリクエストを検査するマシンのCPUが世界中のフリートで100%に張り付き，ルールがロールバックされるまで数百万のサイトのトラフィックが止まりました．

どちらの会社も優秀なエンジニアを抱えていますし，どちらの正規表現もレビューされていました．問題は不注意ではありません．「敵対的な形の入力で指数的になる」という性質が，テストでは見えず，本番では容赦ない．それが問題です．

> [!NOTE]
> バックトラッキングエンジンが間違っているというわけではありません．合理的なトレードオフですし，後方参照のような機能には本質的にバックトラッキングめいたものが必要です．これらの障害の教訓はもっと狭いもので，「指数的になりうるエンジンに，自分の制御下にない入力を渡してはならない」ということです．両社ともその後，影響を受けた経路を線形時間保証のあるエンジンへ移しました．

## 約束を正確に述べておく

これから作るエンジンはひとつの保証をします．後で自分たちをそれに縛れるように，いまのうちに注意深く述べておきましょう．

**マッチングは入力を一度だけ走査し，1ステップにつき1文字を消費し，消費した文字を二度と読み直しません．**各文字に対して微分ステップ(すぐ後で定義します)を1回実行し，その文字を捨てます．巻き戻すべき位置は存在しません．そもそもこのアルゴリズムは位置というものを記憶しないからです．したがって時間は入力の長さに対して線形です．n文字ならnステップ，という感じです．

スローガンより正確さが大事なので，正直な注釈をひとつ．各ステップのコストはパターンに依存します．微分ステップはパターンの木を歩くので，大きくて込み入ったパターンほど1ステップは遅くなります．この保証が締め出すのは破局の方です．ステップあたりのコストは書いたパターンには依存しますが，それまでにどれだけ入力を消費したかにも，入力がどんな見た目かにも，決して依存しません．2^nの崖は設計の中にそもそも存在しない，ということです．

スコープについての安心材料もひとつ．この保証は質素なパターン専用ではありません．`a?`や`+`や`{n,m}`のような便利構文は，保証の対象であるひと握りのコア演算子への変換によって定義されます．なので約束は，`(a?){30}a{30}`を含め，書けるすべてのパターンに自動的に及びます．マッチングが走る頃にはシュガーはもう存在しないので，シュガーが崖を持ち込み直すこともできません．

ステップあたりのコストを小さく保つには実際の作業が必要で(それが[スマートコンストラクタ](./10-smart-constructors.md)の章の主題です)，この約束全体は，まさにこのパターン族の上で，自作した本物のバックトラッカーと対戦して測ります([対決](./19-the-race.md)にて)．

## 忘れられたアイデア: Brzozowski微分

さて，バックトラッキングもせず，状態機械も作らずに，どうやってマッチするのでしょうか?使うのは，Janusz Brzozowskiが1964年に発表したアイデア，正規表現の微分(derivative)です．

直感はこういう感じです．パターンに1文字を食べさせて，こう尋ねます．**「入力がこの文字で始まるなら，入力の残りはどんなパターンにマッチしなければならない?」**その答えもまたパターンで，これを微分と呼びます．

具体例を見ましょう．パターン`abc`の，文字`a`に関する微分はパターン`bc`です．`a`を見た後，残りに見るべきものは`bc`だからです．

`abc`の`x`に関する微分は，何にもマッチしないパターンです．`x`で始まる文字列が`abc`にマッチする見込みは最初からないので，微分はそれを即座に告げます．

`a*`の`a`に関する微分は，再び`a*`です．`a`を1個読んだら振り出しに戻って，喜んで続きを受け付けます．

そうなると，マッチングは拍子抜けするほど単純です．1文字につき1回，左から右へ微分するだけです．パターン`abc`と入力`"abc"`でアルゴリズム全体が動く様子はこんな感じになります．

```
start:            abc
feed 'a', derive: bc
feed 'b', derive: c
feed 'c', derive: (the empty-string pattern)
input exhausted:  does what's left accept the empty string?  yes -> MATCH
```

各ステップは1文字を消費して新しいパターンを生み，古いパターンと古い文字は二度と参照されません．入力が尽きたら，残ったパターンに最後の質問をひとつだけします．「空文字列を受理しますか?」です．この最後の質問が`nullable`という関数で，あまりに中心的なので[専用の章](./07-nullable.md)を用意してあります．

同じパターンに今度は入力`"abx"`を食べさせると，`'x'`のステップで微分は「何にもマッチしないパターン」へ潰れます．失敗は即座に発見され，巻き戻すものは何もありません．

この説明に出てこないものに注目してください．状態なし，遷移表なし，コンパイルフェーズなし，リトライスタックなし．あるのは「1文字ぶん微分する」と「空文字列を受理する?」の2つの関数だけで，どちらもパターンの構造に関する再帰で定義されます．パターンは木で，木の各ケースに等式が1本ずつ与えられ，アルゴリズムは1ページぶんのパターンマッチに収まります．

これこそ，微分がFPネイティブな選択である理由です．代数的データ型の上の再帰関数を中心に組み立てられた言語では，この1964年のアルゴリズムは実装するというより書き写すものに近いです．(前の章で1行の`matches`を見た人へ:あのfoldがこのループです．何を畳み込んでいたのか，これで分かったかと思います．)

「これで全部なら話がうますぎるのでは?」と感じたなら，良い直感です．木としてのパターンは微分を取るたびに成長することがあり，その成長を制御するところにエンジニアリングが宿ります．とはいえそれらは，1ページに収まるコアへの改良にすぎません．そしてそのコアは，4つの章のうちに本物の文字列にマッチするようになります．

## まとめ

- 正規表現は小さな言語です．各パターンは文字列の集合を表し，マッチングは帰属についての質問にひとつ答えます．
- エンジンは3つの系統に分かれます．バックトラッキング(Python，JavaScript，Java，PCREなど．指数的になるまでは高速)，オートマトン(RE2やRustの`regex`．状態機械による線形時間)，そして微分(本書の選択．パターンそのものの上の再帰関数による線形時間)です．
- 壊滅的バックトラッキングとは，選択点の組合せ的な再探索です．`(a?){3}a{3}`は`"aaa"`に対してすでに8通りを探索し，`(a?){n}a{n}`は2^n通りを探索します．ReDoS攻撃や，2016年のStack Overflowと2019年のCloudflareの障害の背後にある機構です．
- 本書の約束を正確に言うと，一度の走査，1文字につき1微分ステップ，消費済みの入力は二度と読まない，です．ステップあたりのコストはパターンに依存し，それまでの入力量には決して依存しません．
- Brzozowski微分(1964年)は「この文字の後，残りは何にマッチすべきか?」に答えます．マッチングは微分の畳み込みと，最後の`nullable`チェックひとつです．すべては木の上の再帰関数です．
- 本書は4部構成です．イントロダクション，コアエンジン，実用への道，Idrisパワーアップ．

この理論をコードにする前に，まずはマシンにIdris 2が必要です．というわけで，[環境構築](./03-setup.md)に進みましょう．
