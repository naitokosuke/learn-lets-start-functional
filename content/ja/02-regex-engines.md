# 正規表現エンジンとは

[前の章](./01-why-functional.md)では、悪役と、それを打ち倒す忘れられたアイデアを約束しました。この章はその両方をお届けし、本書の残りのロードマップで締めくくります。

## 文字列の集合を表す小さな言語

まとわりつく俗説をはぎ取ってしまえば、正規表現はとても小さなものです。*文字列の集合を記述するための記法*——それだけです。

パターン `abc` は、文字列 `"abc"` ただ 1 つを要素とする集合を記述します。パターン `a|b` は、`"a"` と `"b"` の 2 要素からなる集合を。パターン `a*` は無限集合を記述します。`""`、`"a"`、`"aa"`、`"aaa"`、と、どこまでも。

正規表現構文のすべての演算子は、小さな集合からより大きな集合を組み立てる方法です。連接は端と端をつなぎ、`|` は合併し、`*` は繰り返す。(名前の由来が気になる人へ:1950 年代の Stephen Kleene による「正規事象(regular events)」の研究にさかのぼります。`*` は彼にちなんでクリーネスターと呼ばれます。正規表現は、あなたのツールチェーンにあるほとんど何よりも年上なのです。)

「この文字列はこのパターンにマッチする?」と尋ねるとき、実際に尋ねているのは「この文字列は、このパターンが記述する集合の要素?」ということです。それが正規表現エンジンの職務内容のすべてです。パターンと文字列を受け取り、帰属についての質問にひとつ答える。

この見方——パターンは*記述*であり、マッチングはその記述するものへの帰属を確かめることである——は、哲学的な言葉遊びに聞こえるかもしれません。ところが実は、これこそ本書のエンジニアリング上の心臓部です。記述とは、ただのデータです。そして関数型言語において、データ構造の上の関数は、私たちが一日中やっていることそのものです。この考えを、覚えておいてください。

## エンジンの 3 つの系統

帰属の判定は驚くほど多様な方法で実装でき、世に存在するほぼすべての正規表現エンジンは、3 つの系統のどれかに属します。

**バックトラッキングエンジン**は、あなたがほぼ間違いなく毎日使っているものです。Python の `re`、JavaScript の `RegExp`、Java の `java.util.regex`、Ruby、Perl、PCRE。これらはパターンを小さなプログラムとして扱い、再帰的に実行します。この選択肢を試し、後続のマッチが失敗したら、戻ってきてもう一方を試す。バックトラッキングは実装が簡単で、後方参照のような非正規の機能へ自然に拡張でき、たいていは高速です。*たいていは。* その失敗モードが次の節の主題です。

**オートマトンエンジン**は、マッチングの前にパターンを有限状態機械へコンパイルします——事前に(DFA)、あるいはその場で(NFA シミュレーション)。Google の RE2 と Rust の `regex` クレートが有名どころです。これらは線形時間のマッチングを保証します。どんな入力でも爆発させることはできません。それこそが存在理由です——RE2 は、Google が信頼できないユーザーからの正規表現を受け付けられるように、まさにそのために作られました。

オートマトン方式の代償は、コンパイルフェーズと、本物のエンジニアリング的複雑さを伴う状態機械の構築、そして後方参照をあきらめることです。(このトレードは割に合うと、業界も少しずつ認めつつあります。たとえば .NET は現在、従来のエンジンと並べて、オプトインの非バックトラッキングモードを出荷しています。)

**微分エンジン**——私たちの選択——は、ほとんど知られていない第 3 の系統です。状態機械へのコンパイルなし、バックトラッキングなし。パターンそのものが、データ構造として 1 文字ずつ変換されていき、最後に答えがこぼれ落ちます。オートマトン系と同じ線形時間の保証を持ちながら、上から下まで、木の上のひと握りの再帰関数のままでいられるのです。

このアイデアは 1964 年に生まれ、40 年間文献の中で眠り、関数型プログラマたちの手で揺り起こされました。2009 年の論文——その名も「Regular-expression derivatives re-examined(正規表現の微分・再考)」——は、関数型言語ではこの技法が実用的であるどころか*快適*であることを見出しました。本書がたどり直すのは、この再発見です。アイデアそのものとは、すぐ後できちんとご対面します。

## 悪役:壊滅的バックトラッキング

まずは、主流の設計が破綻する様子を見物しましょう。このパターンを考えます(構文 `a?` は「`a` が 1 個、または何もなし」、`{3}` は「3 回」の意味です)。

```
(a?){3}a{3}
```

書き下せば `a?a?a?aaa` です。これを入力 `"aaa"` にマッチさせてみます。

バックトラッキングエンジンは左から右へ動作し、各 `a?` は*選択点(choice point)*です。貪欲に `a` を 1 個消費しようとし、この場所を覚えておく——後で何かが失敗したら、ここに戻ってきて、今度は何も消費しない方を試すためにです。エンジンの記憶は、まるごとこの「リトライすべき場所」のスタックです。動きを追ってみましょう。

```
attempt 1: a? a? a? each eat one 'a'   -> "aaa" consumed, a{3} needs 3 more -> FAIL
attempt 2: first two eat, third skips  -> "aa" consumed,  a{3} needs 3, 1 left -> FAIL
attempt 3: 1st and 3rd eat, 2nd skips  -> "aa" consumed,  1 left  -> FAIL
attempt 4: only the first eats         -> "a" consumed,   2 left  -> FAIL
attempt 5: 2nd and 3rd eat, 1st skips  -> "aa" consumed,  1 left  -> FAIL
attempt 6: only the second eats        -> "a" consumed,   2 left  -> FAIL
attempt 7: only the third eats         -> "a" consumed,   2 left  -> FAIL
attempt 8: all three skip              -> "" consumed,    3 left  -> MATCH
```

独立した二択が 3 つあるので、エンジンは最大 2 × 2 × 2 = 8 通りの組み合わせを探索します——しかも成功する組み合わせは、探索順のどん尻です。*何を繰り返しやり直しているか*にも注目してください。試行 2、3、5 はどれも `a` を 2 個消費して同一の理由で失敗しますが、エンジンにはそれらが同じ状況だと気づくすべがありません。覚えているのはリトライする場所であって、学んだ内容ではないのです。

では一般化します。`(a?){n}a{n}` を n 個の `a` からなる文字列にマッチさせると、エンジンは 2^n 通りの組み合わせに直面します。n = 10 なら千通りで、誰も気づきません。n = 20 なら百万通りで、リクエストが遅くなります。n = 30 なら十億通り——あなたのリクエストハンドラは、いまや暖房器具です。入力は大きくある必要すらありませんでした——たった 30 文字!——ただ*形*が悪ければよかったのです。

これが壊滅的バックトラッキングです。そして肝心なことに、パターンの見た目は完全に無害です。`(a?){30}a{30}` をわざわざ書く人はいませんが、繰り返しが入れ子になったり隣り合ったりする現実のパターン——たとえば `(\s*.*)+`——は、同じ爆発的構造を隠し持っています。そういうパターンはコードレビューをすり抜けます。誰かが試そうと思いついたすべての入力で、完璧に*動く*からです。

指数の崖が現れるのは、ちょうど悪い形をした入力に対してだけ。つまり、攻撃者が送ってくる入力に対してです。これを意図的に悪用する行為には名前が付いています——ReDoS、正規表現サービス拒否攻撃(regular expression denial of service)です。

## 2 つの有名な障害

実際の事件は、どんな理屈よりも雄弁です。

2016 年 7 月、Stack Overflow は 30 分あまりダウンしました。引き金は行末の空白を取り除く正規表現で、それがおよそ 2 万個の連続した空白文字を含む投稿に適用されたのです。そのたった 1 つの文字列に対するバックトラッキングは約 2 億回の文字比較に相当し——二次関数的で、指数的ですらありませんが、それで十分でした——レンダリング経路の CPU を張り付かせました。ヘルスチェックがタイムアウトし、ロードバランサがサイトをローテーションから外しました。

2019 年 7 月、Cloudflare——ウェブ全体の無視できない割合を担う——は、約 30 分にわたって全世界で 502 エラーを返しました。新しくデプロイされた WAF(ウェブアプリケーションファイアウォール)のルールに、核心部が `.*.*=.*` に相当する正規表現が含まれていたのです。特定の入力でそれが壊滅的にバックトラックし、すべてのリクエストを検査するマシンの CPU が世界中のフリートで 100% に張り付き、ルールがロールバックされるまで数百万のサイトのトラフィックが止まりました。

どちらの会社も優秀なエンジニアを抱えています。どちらの正規表現もレビューされていました。問題は不注意ではありません。「敵対的な形の入力で指数的になる」という性質が、テストでは見えず、本番では容赦ない——それが問題なのです。

> [!NOTE]
> バックトラッキングエンジンが*間違っている*わけではありません——合理的なトレードオフですし、後方参照のような機能には本質的にバックトラッキングめいたものが必要です。これらの障害の教訓はもっと狭いものです。指数的になりうるエンジンに、自分の制御下にない入力を渡してはならない。両社ともその後、影響を受けた経路を線形時間保証のあるエンジンへ移しました。

## 私たちの約束を、正確に

これから作るエンジンはひとつの保証をします。後で自分たちをそれに縛れるよう、いまここで注意深く述べておく価値があります。

**マッチングは入力を一度だけ走査し、1 ステップにつき 1 文字を消費し、消費した文字を二度と読み直しません。** 各文字に対して*微分ステップ*(すぐ後で定義します)を 1 回実行し、その文字を捨てます。巻き戻すべき位置は存在しません。このアルゴリズムは、そもそも位置というものを記憶しないからです。したがって時間は入力の長さに対して線形です。n 文字なら、n ステップ。

スローガンより正確さが大事なので、正直な注釈をひとつ。*各ステップのコストはパターンに依存します。* 微分ステップはパターンの木を歩くので、大きい、あるいは込み入ったパターンほど 1 ステップは遅くなります。この保証が締め出すのは、破局の方です。ステップあたりのコストはあなたの書いたパターンに依存しますが、それまでにどれだけ入力を消費したかにも、入力がどんな見た目かにも、決して依存しません。2^n の崖は、設計の中にそもそも存在しないのです。

スコープについての安心材料もひとつ。この保証は、質素なパターン専用ではありません。`a?` や `+` や `{n,m}` のような便利構文は、保証の対象であるひと握りのコア演算子への*変換によって*定義されます——つまり約束は、`(a?){30}a{30}` を含め、あなたが書けるすべてのパターンへ自動的に及びます。シュガーが崖を持ち込み直すことはできません。マッチングが走る頃には、シュガーはもう存在しないのですから。

ステップあたりのコストを小さく保つには実際の作業が必要で——それが[スマートコンストラクタ](./10-smart-constructors.md)の章の主題です——そしてこの約束全体を、まさにこのパターン族の上で、自作した本物のバックトラッカーと対戦して測ります。[対決](./19-the-race.md)にて。

## 忘れられたアイデア:Brzozowski 微分

では、バックトラッキングもせず、状態機械も作らずに、どうやってマッチするのでしょう?Janusz Brzozowski が 1964 年に発表したアイデア——正規表現の*微分(derivative)*を使うのです。

直感の全体はこうです。パターンに 1 文字を食べさせて、こう尋ねます。**「入力がこの文字で始まるなら、入力の*残り*はどんなパターンにマッチしなければならない?」** その答えもまたパターンであり、これを*微分*と呼びます。

具体的に。パターン `abc` の、文字 `a` に関する微分はパターン `bc` です——`a` を見た後、残りに見るべきものは `bc` です。

`abc` の `x` に関する微分は、何にもマッチしないパターンです。`x` で始まる文字列が `abc` にマッチする見込みは端からなく、微分はそれを即座に告げます。

`a*` の `a` に関する微分は、再び `a*` です——`a` を 1 個読んだら、振り出しに戻って、喜んで続きを受け付けます。

そうなると、マッチングは拍子抜けするほど単純です。1 文字につき 1 回、左から右へ微分するだけ。パターン `abc` と入力 `"abc"` でアルゴリズム全体が動く様子をどうぞ。

```
start:            abc
feed 'a', derive: bc
feed 'b', derive: c
feed 'c', derive: (the empty-string pattern)
input exhausted:  does what's left accept the empty string?  yes -> MATCH
```

各ステップは 1 文字を消費して新しいパターンを生み、古いパターンと古い文字は二度と参照されません。入力が尽きたら、残ったパターンに最後の質問をひとつ。「空文字列を受理しますか?」この最後の質問が `nullable` という関数で、あまりに中心的なので[専用の章](./07-nullable.md)が用意されています。

同じパターンに今度は入力 `"abx"` を食べさせると、`'x'` のステップで微分は「何にもマッチしないパターン」へと潰れます——失敗は即座に発見され、巻き戻すものは何もありません。

この説明に*出てこないもの*に注目してください。状態なし、遷移表なし、コンパイルフェーズなし、リトライスタックなし。あるのは 2 つの関数——「1 文字ぶん微分する」と「空文字列を受理する?」——だけで、どちらもパターンの構造に関する再帰で定義されます。パターンは木であり、木の各ケースに等式が 1 本ずつ与えられ、アルゴリズムは 1 ページのパターンマッチへ溶けていきます。

これこそ、微分が FP ネイティブな選択である理由です。代数的データ型の上の再帰関数を中心に組み立てられた言語では、この 1964 年のアルゴリズムは*実装する*というより*書き写す*ものに近いのです。(前の章で 1 行の `matches` を見た人へ:あの fold がこのループです。何を畳み込んでいたのか、これで分かりましたね。)

これで全部なら話がうますぎる、と感じたなら——良い直感です。木としてのパターンは微分を取るたびに成長することがあり、その成長を制御するところにエンジニアリングが宿ります。とはいえそれらは、1 ページに収まるコアへの改良にすぎません。そしてそのコアは、4 つの章のうちに本物の文字列にマッチするようになります。

## まとめ

- 正規表現は小さな言語です。各パターンは文字列の集合を表し、マッチングは帰属についての質問にひとつ答えます。
- エンジンは 3 つの系統に分かれます。バックトラッキング(Python、JavaScript、Java、PCRE——指数的になるまでは高速)、オートマトン(RE2、Rust の `regex`——状態機械による線形時間)、そして微分(私たちの選択——パターンそのものの上の再帰関数による線形時間)。
- 壊滅的バックトラッキングとは、選択点の組合せ的な再探索です。`(a?){3}a{3}` は `"aaa"` に対してすでに 8 通りを探索し、`(a?){n}a{n}` は 2^n 通りを探索します——ReDoS 攻撃、そして 2016 年の Stack Overflow と 2019 年の Cloudflare の障害の背後にある機構です。
- 私たちの約束を正確に言えば:一度の走査、1 文字につき 1 微分ステップ、消費済みの入力は二度と読まない。ステップあたりのコストはパターンに依存し、それまでの入力量には決して依存しない。
- Brzozowski 微分(1964 年)は「この文字の後、残りは何にマッチすべきか?」に答えます——マッチングは微分の畳み込みと、最後の `nullable` チェックひとつ。すべては木の上の再帰関数です。
- 本書は 4 部構成です。イントロダクション、コアエンジン、実用への道、Idris パワーアップ。

この理論がコードになる前に、あなたのマシンには Idris 2 が必要です——というわけで、[環境構築](./03-setup.md)へ。
