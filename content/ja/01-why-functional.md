# なぜ関数型?なぜIdris?

この章の仕事はひとつだけです．この先の数百ページが読む価値のあるものだと納得してもらうことです．まだコードは書きません．とりあえず，計画とその理由だけ話させてください．

## 評判の問題

関数型プログラミングには評判の問題があります．しかも，その大半は自業自得だったりします．

一度でも入門しようとしたことがあれば，お決まりの流れはご存じかと思います．「モナドとは」で検索するとブリトーが出てきます．宇宙服やら箱やらベルトコンベアやらを眺めているうちに，例の有名な「モナドは自己関手の圏におけるモノイドにすぎない．何か問題でも?」にたどり着きます．

あるいはちゃんとしたチュートリアルを開いてみると，ラムダ計算や圏論，もしくは動くコードを1行も書かないうちに暗記させられる代数法則の一覧から始まったりします．そして3ページ目あたりで静かにタブを閉じて，ちゃんと出荷できるコードを書く日常に戻ってしまうわけです．

もどかしいのは，こういった教材が別に間違ってはいないという点です．ただ，順番が逆さまなだけです．抽象を先に教えて，動機が後から追いついてくることを祈っている．車の運転を熱力学の講義から教えるようなもので，基礎としては正しくても，最初の一歩としてはほとんど役に立ちません．

ただ，プログラミングパラダイムの学び方自体は，みなさんすでに知っているはずです．オブジェクト指向をリスコフの置換原則の勉強から始めた人はあまりいないでしょう．何かを作って，言語に押し返されて，その作業の中で概念が固まっていく．そういう学び方だったかと思います．

本書でやるのもまさにそれです．**小さくて本物の役に立つものをひとつ作り，登場する言語機能それぞれに存在価値を証明してもらう．**これが本書の方針です．美しいからという理由で導入される機能はひとつもありません．どの機能も，いま書いているコードがまさにいま必要としているから登場しますし，それが元を取る様子をその場で見届けられます．

理論の講義は省略するので，代わりに本書で使うざっくりした定義だけ置いておきます．関数型プログラミングとは，数学的な意味での関数でソフトウェアを組み立てることです．出力は入力だけで決まり，関数を呼び出しても世界は何も変わらない．これだけです．

このスタイルの利点としてよく挙がるもの(テストのしやすさ，恐れずにできるリファクタリング，目の前の部分を読むだけで理解できるコード)は，すべてこのひとつの性質から導かれます．逆に，風変わりに見えるものはすべて，実用的な仕事をこなしながらこの性質を守り抜くためのエンジニアリングです．種明かしはこれで全部で，残りのページはその実践という感じです．

## 題材:正規表現エンジン

作るのは正規表現エンジンです．`a*b`にマッチして一丁上がり，というおもちゃではなく，文字クラス，エスケープ，`a{2,4}`のような回数指定の繰り返し，パターン構文のパーサ，プリティプリンタ，実際に使える公開APIまで備えた本物のエンジンです．これをテストファーストで，小さなステップを積み重ねながら書いていきます(各ステップはバージョン管理にも残します)．

なぜよりによって正規表現エンジンなのか?理由は3つあります．

**1つ目は，それが何をすべきものか，すでに知っているからです．** `\w+@\w+`くらいは誰でも一度は書いたことがあるかと思います．問題領域の説明にページを割く必要がないので，すべてのページを面白い部分，つまり解法がどう動くかに使えます．「`colou?r`はcolorとcolourの両方にマッチすべき」というテストを見て，説得が必要な人はいないはずです．

**2つ目は，正規表現エンジンが関数型プログラミングのホームグラウンドだからです．**パターンの表現も，マッチングアルゴリズムも，パーサもプリンタも，全部が木を変換する純粋な関数です．データベースもネットワークもUIもありません．エンジン全体で外の世界に触れる関数は，結果を表示するテストランナーのちょうど1つだけで，あとはすべて値が入って値が出ていくだけです．関数で考える練習の最初の題材として，これ以上のものはなかなかないかと思います．

**3つ目は，悪役がいることです(これが一番の目玉です)．** PythonやJavaScript，Java，Rubyといった主流の正規表現エンジンは，壊滅的バックトラッキング(catastrophic backtracking)と呼ばれる設計上の欠陥を共有しています．一見無害なパターンが，特定の入力に対して指数関数的な時間を食ってしまうというものです．机上の珍現象ではなく，実際にStack OverflowやCloudflareを落としていますし，サービス拒否攻撃のひとつのカテゴリを支えてもいます．

本書のエンジンはこれに対して免疫を持ちます．タイムアウトを仕込むからでも，賢い仕掛けを一枚かぶせるからでもなく，心臓部の純関数型アルゴリズムがそもそもバックトラックできないからです．どんなパターンもどんな入力も，左から右への一度の走査でマッチします．この悪役と倒し方の詳細は，まるごと[次の章](./02-regex-engines.md)で扱います．

## 完成形を先にちょっとだけ

イメージを掴むために，完成したエンジンのマッチングアルゴリズム全体を先にお見せします．パターンが文字列にマッチするかどうかを決める，リポジトリにある実際のコードです．

```idris
matches : Regex -> String -> Bool
matches r s = nullable (foldl (flip deriv) r (unpack s))
```

たった1行です．いま読める必要はまったくありません(そのための本書です)が，見て取れるものには注目してみてください．ループなし，可変なマッチ状態なし，リトライ用のスタックなし．あるのは2つの補助関数(`nullable`と`deriv`，それぞれ6行ほど)と，入力の文字列に対する1回の畳み込み(fold)だけです．[コアエンジンのパート](./09-matches.md)を終える頃には，この行を自分の手でテストファーストで書き上げていて，むしろ当たり前のコードに見えているはずです．

そして，完成したエンジンが実際に仕事をしている様子がこちらです(クローンして`regex/`ディレクトリで`make repl`を実行したときの対話セッションです．クローンのコマンドは後述します)．

```repl
Main> :module Regex
Imported module Regex
Main> :exec printLn (test "colou?r" "my favourite colour")
Right True
Main> :exec printLn (test "gr[ae]y" "a green wall")
Right False
```

本物のパターン構文が入力され，自作のパーサでパースされ，さっきの1行でマッチされています．(`Right`というラッパーは「パターン自体は正しい形でしたよ」というエンジンからの報告です．この話は[公開API](./15-public-api.md)の章でやります．)

これが本書全体を貫くパターンです．微分ベースのマッチングやパーサコンビネータ，機械検証された証明といった高度そうな話も，言語が問題にフィットしていれば案外小さく収まります．関数型プログラミングの要点は知的な洗練ではなく，コードが短くなると同時に信頼できるようになることです．

## なぜHaskellではなくIdris 2?

関数型プログラミングの入門先としてまず名前が挙がるのはたぶんHaskellです．なので，Idris 2を選ぶ理由は先に説明しておきます．IdrisはHaskellファミリーの関数型言語で，Haskellを見たことがあれば構文はかなり見覚えのあるものになるはずです．ただ，いくつかの点でHaskellとは違う選択をしていて，最初の関数型言語としては，その選択がどれも学ぶ側に有利に働きます．

**Idrisは正格(strict)評価で，遅延(lazy)評価ではありません．** Haskellの式は遅延評価されます．書いた時点ではなく，いつか何かがその値を要求した時点で評価されるということです．遅延評価は強力ですが，「いつ処理が走るのか」「どれだけメモリを使うのか」の直感をゼロから作り直す必要があり，この作り直しがHaskellの学習曲線が急な理由のひとつです．

IdrisはPythonやJavaScriptやRustと同じ先行評価です．引数が計算されてから関数が走る．性能に関する既存のメンタルモデルはほぼそのまま持ち越せます．(Haskell勢へ:そうです，デフォルトでは遅延無限リストもありません．Idrisには明示的な`Inf`型がありますが，本書では使いません．)

**やり方がだいたい1通りしかありません．** Haskellは数十年分の拡張と複数の文字列型，何をするにも5つのライブラリが揃った巨大な言語です．Idris 2は小さくて新しい言語なので，道はよく整備されています．文字列型は1つ，`point.x`のようなドットアクセスが最初から付いてくるレコード構文が1つ，do記法もインターフェースも初日から組み込みです．選ぶ時間が減って，作る時間が増えます．

**ホール(hole)がコンパイラをペアプロ相手にしてくれます．** Idrisでは`?`で始まる名前で穴を開けたままプログラムを書くことができて，コンパイラはそこに収まるべきものの型と，それを組み立てるために手元にあるものを正確に教えてくれます．

コードを書いてから型チェッカーと口論するのではなく，型チェッカーと会話しながら書く感じです．このワークフローは型付き言語のオンボーディング機能としてトップクラスに優秀で，[速習コース](./04-idris-crash-course.md)で主役を張ります．

**全域性(totality)チェッカーが誠実さを教えてくれます．** Idrisは関数が全域(total)であること，つまり起こりうるすべての入力を処理して必ず停止することを検査できます．本書ではこれをエンジン全体で有効にします．アカデミックに聞こえるかもしれませんが，実際には，忘れていた`case`や終わらない再帰をコンパイル時に捕まえてくれる疲れ知らずのレビュアーです．しかも終盤の章で，これが[テストを定理に変える](./18-proofs.md)ための鍵だったとひっそり判明します．

そして，この選択を安全にしてくれる事実がひとつあります．**本書で学ぶことはすべてHaskellに一対一で対応します．**代数的データ型，パターンマッチ，高階関数，インターフェース(Haskellでは型クラスと呼びます)，モノイド，ファンクタ，do記法，パーサコンビネータ．どれもそのまま持ち越せて，大半は同一かほぼ同一の構文です．

これは意図的な設計です．メインストリーム言語の代わりにニッチな言語を学ぶのではなく，MLファミリー全体に共通する核を，その一番フレンドリーなメンバーを通して学ぶという話です．[最終章](./21-whats-next.md)には，Haskellに移りたくなったときのためのIdris→Haskell対応表も用意してあります．

> [!NOTE]
> Idrisの一番の有名どころは依存型(dependent types)です．値に依存できる型のことで，プログラムについての証明を書けるようになります．本書でも終盤で本物の依存型をひと口だけ味わいますが，あくまでデザートであってメインディッシュではありません．依存型を知らなくても読み進められますし，知っている前提の書き方もしません．

## 数学は必要?

必要ないです．そして，なぜ必要ないのかはきちんと書いておく価値があるかと思います．理論ファーストの教え方が植え付けたのが，まさにこの恐怖だからです．

数学の血筋を持つ言葉にはいくつか出会うことになります．モノイドは，作ったエンジンの中に実は2つ潜んでいたと判明したときに登場しますし，マッチングアルゴリズムの名前はそのまま微分(derivative)です．ただ，どの場合も言葉はコードの後にやって来ます．すでに作ってテストし終えたものに名前が付くだけです．自分が作ったものに立派な名前があったと知るのは，名前を理解するまで作るなと言われるよりずっといい気分かと思います．

そして例のモナドについて．本書にモナドのチュートリアルはありません．do記法は作用を順番に並べる必要が出てきたときに登場し，その仕組みは自作パーサのコードがそのパターンを目に見える形にしたとき([パーサコンビネータ](./13-parser-combinators.md)のあたり)に説明します．ブリトーは最後まで登場しません．

## 作らないもの

スコープについては最初に正直に書いておきます．本書のエンジンはクラス，エスケープ，選択，繰り返し，回数指定といった本物のパターンにマッチしますが，あくまでマッチャーであって，完全なPCREクローンではありません．具体的には，次のものは作りません．

- **キャプチャグループ**:丸括弧のグループがマッチした部分文字列を取り出す機能です．本書の丸括弧はグループ化はしますが，キャプチャはしません．
- **アンカー**(`^`や`$`):本書の`match`は定義からして文字列全体のマッチで，文字列内の検索用には別途`contains`を作ります．
- **後方参照**(`(\w+) \1`のような):これらはそもそも正規言語ではなく，エンジンをバックトラッキングに追い込む張本人です．
- **Unicode文字カテゴリ**(`\p{Greek}`のような):本書の文字集合は範囲と否定を扱えるので，アイデアを学ぶにはそれで十分です．
- **RE2流の最適化DFAコンパイラ**:本書のエンジンはそれなしでも線形時間です(そのぶん定数倍のコストは少し払います)．

どれも不可能だから省くわけではありません(大半は[この先へ](./21-whats-next.md)に演習のスケッチとして再登場します)．本書のすべての章は関数型プログラミングを教えるために存在していて，これらの機能はレッスンというより正規表現の話になってしまう．なので省く，というだけです．

## コミット履歴こそが本書

さて，始める前にもうひとつだけ．この先の読み方に関わる話です．

本書は「書いてから実装した」ものではありません．コミットされたものです．コードを作る章はすべて，リポジトリの実際のコミットに対応しています．まず失敗するテストを追加するコミット(`(red)`と記されます)，続いてそれを通す最小の実装のコミット(`(green)`)です．物語の中盤にある実際のペアを，`git log`の表示そのままでどうぞ．

```
d1a0950 test(core): specs for matches, end to end (red)
d8e7c5c feat(core): matches — fold deriv, then ask nullable (green)
```

履歴がそのままチュートリアルになっています．どのコミットをチェックアウトしても，本書のどこかの一文に正確に対応した場所に立てますし，コードは本文が説明するとおりの状態になっています．

とりあえず，いまのうちにクローンしておきましょう．

```sh
git clone https://github.com/ubugeeei-prod/lets-start-functional.git
```

`regex/`ディレクトリがエンジンで，`content/`がいま読んでいる本文です．中で`git log --oneline`を実行すると，一番下の最古のコミットからscaffold，red，green，red，greenと続き，最後は自作エンジンの上に築いた動くレキサまで，物語全体が並んでいるのが見えます．

コミットを再生しながら読み進める必要はありません(必要なコードはすべて本文に載せます)が，履歴がそこにあると知っていると読み方が少し変わるかと思います．本書に擬似コードは1行もありません．すべて実際に動いたものですし，動くところを自分の目で確かめられます．

## まとめ

- 関数型プログラミングの評判の問題は，動機より先に抽象を教えることから来ています．本書はその順番を逆転させて，ひとつの本物のプロジェクトの中で各機能に存在価値を証明してもらいます．
- そのプロジェクトが正規表現エンジンです．なじみのある問題で，木の上の純粋な関数だけで完結する領域で，しかも設計そのもので打ち倒せる現実の悪役(壊滅的バックトラッキング)がいます．
- 完成したエンジンのマッチングアルゴリズムは，2つの小さな補助関数の上に乗った1行のコードです．正しい土台があれば難しいことは小さくなる，という本書で繰り返されるレッスンの予告編でもあります．
- Idris 2を選ぶのは，正格で(性能の直感がそのまま生きる)，小さく(やり方が明白)，対話的で(ホールがコンパイラを協力者に変える)，誠実(全域性チェッカー)だからです．しかも学んだことはすべてHaskellに一対一で移り，最終章に対応表があります．
- 作るのはマッチャーであってPCREクローンではありません．キャプチャグループ，アンカー，後方参照，Unicodeカテゴリ，DFAコンパイルはなしです(どう作るかは[この先へ](./21-whats-next.md)を参照してください)．
- リポジトリのコミット履歴こそが本書です．redのテストコミットとgreenの実装コミットが並んでいて，どのステップからでも再生できます．

次はいよいよ悪役とのご対面です．正規表現エンジンとは実際のところ何なのか，主流のエンジンはどう爆発するのか，そして本書のエンジンを安全に保つ1964年の忘れられたアイデアとは何か．[正規表現エンジンとは](./02-regex-engines.md)に進みましょう．
