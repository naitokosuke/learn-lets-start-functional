# なぜ関数型?なぜ Idris?

本書最初のこの章の仕事はただひとつ——この先の数百ページがあなたの時間を割く価値のあるものだと、納得してもらうことです。まだ書くコードはありません。ここにあるのは計画と、その背後にある理由だけです。

## 評判という問題

関数型プログラミングにはマーケティング上の問題があります。しかもその大半は自業自得です。

一度でも学ぼうとしたことがあれば、お決まりの流れはご存じでしょう。「モナドとは何か」と検索すると、ブリトーが出てくる。宇宙服が、箱が、ベルトコンベアが出てくる。そして悪名高い「モナドは自己関手の圏におけるモノイドにすぎない。何か問題でも?」にたどり着きます。

あるいは、ちゃんとしたチュートリアルを開いてみると、ラムダ計算から始まります。もしくは圏論から。もしくは、何かが実際に動く行を 1 行も書かないうちに暗記させられる、代数法則の壁から。3 ページ目あたりであなたは静かにタブを閉じ、ちゃんと出荷できるコードを書く日常に戻っていくのです。

もどかしいのは、そうした教材のどれひとつとして*間違ってはいない*ことです。ただ、上下が逆さまなのです。抽象を先に教え、動機が後から追いついてくることを祈っている。それは熱力学の講義から車の運転を教えるようなもの——技術的には基礎でも、最初の一歩としてはまるで役に立ちません。

でも、思い出してください。あなたはすでにプログラミングパラダイムの学び方を知っています。前にも一度やっているのですから。オブジェクト指向を、リスコフの置換原則の勉強から学んだわけではないでしょう。何かを作り、言語に押し返され、その作業の中から概念が結晶していった——そうやって学んだはずです。

本書でやるのも、まさにそれです。本書のテーゼはシンプルです。**小さくて、本物で、役に立つものをひとつ作り、道中で登場するすべての言語機能に、その存在価値を証明させる。** 美しいからという理由で導入されるものは何ひとつありません。どの機能も、いま書いているコードが*まさにいま*それを必要としているから登場し、それが元を取る瞬間をあなたはその場で見届けることになります。

理論の講義は省略するので、代わりに本書で使う実用的な定義をここに置いておきます。一息で言い切れるものです。関数型プログラミングとは、*数学的な意味での関数*でソフトウェアを組み立てることです。出力は入力だけで決まり、それ以外の何にも依存しない。そして、関数を呼び出しても世界は何も変わらない。

このスタイルについて人々が称賛するもの——テストのしやすさ、恐れ知らずのリファクタリング、目の前の部分を読むだけで理解できるコード——は、すべてこのひとつの性質から導かれます。そして、風変わりに見えるものはすべて、有用な仕事をこなしながらこの性質を握りしめておくために必要なエンジニアリングにすぎません。秘密はこれで全部です。残りのページは、その実践です。

## 小さくて、本物で、役に立つもの:正規表現エンジン

作るのは正規表現エンジンです。`a*b` にマッチしたら一丁上がり、というおもちゃではありません——文字クラス、エスケープ、`a{2,4}` のような回数指定の繰り返し、パターン構文のパーサ、プリティプリンタ、そして実際に使える公開 API を備えた、本物のエンジンです。そのすべてをテストファーストで、小さなステップを重ねて書き、各ステップをバージョン管理に残していきます。

よりによってなぜ正規表現エンジンなのか?理由は 3 つあります。

**第一に、それが何をすべきものか、あなたはもう知っています。** 誰でも一度は `\w+@\w+` と書いたことがあるはずです。問題領域の説明に割くページはゼロで済み、すべてのページを面白い部分——解法がどう動くか——に使えます。`colou?r` は color と colour の両方の綴りにマッチすべきだ、というテストを見て、説得が必要な人はいないでしょう。

**第二に、正規表現エンジンは関数型プログラミングのホームグラウンドです。** パターンの表現も、マッチングアルゴリズムも、パーサもプリンタも——全体が、木を変換する純粋な関数です。データベースもネットワークも UI もありません。エンジン全体で外の世界に触れる関数はちょうど 1 つ(結果を表示するテストランナー)だけで、それ以外はすべて、値が入って値が出ていくだけ。関数で考えることを学ぶ最初のプロジェクトとして、これ以上のものは狙って設計しようとしても作れません。

**第三に——これが一番の目玉ですが——悪役がいます。** 主流の正規表現エンジン——Python、JavaScript、Java、Ruby のもの——は、*壊滅的バックトラッキング(catastrophic backtracking)*と呼ばれる設計上の欠陥を共有しています。一見無害なパターンが、特定の入力に対して指数関数的な時間を要するのです。これは机上の珍現象ではありません。Stack Overflow と Cloudflare を実際に落とし、サービス拒否攻撃のひとつのカテゴリを支えています。

私たちのエンジンはこれに免疫を持ちます。タイムアウトをまぶすからでも、小賢しい仕掛けを一枚かぶせるからでもなく、心臓部にある純関数型のアルゴリズムが、そもそもバックトラック*できない*からです。どんなパターンもどんな入力も、左から右への一度の走査でマッチします。この悪役と、それをどう打ち倒すのかは、まるごと[次の章](./02-regex-engines.md)で扱います。

## 目的地をひと目

話を具体的にするために、完成したエンジンのマッチングアルゴリズム全体をお見せします。パターンが文字列にマッチするかどうかを決める、実際のリポジトリにある実際のコードです。

```idris
matches : Regex -> String -> Bool
matches r s = nullable (foldl (flip deriv) r (unpack s))
```

たった 1 行。いま読める必要はありません——そのための本書です——が、*見て取れるもの*には注目してください。ループなし、可変なマッチ状態なし、リトライ用のスタックなし。2 つの補助関数(`nullable` と `deriv`、それぞれ 6 行ほど)と、入力の文字列に対するひとつの畳み込み(fold)だけです。[コアエンジンのパート](./09-matches.md)を終える頃には、この行をあなた自身がテストファーストで書き上げていて、ほとんど当たり前のことに感じられるはずです。

そしてこちらが、完成したエンジンが仕事をしている様子——今日のリポジトリそのままの状態に対する対話セッションです(クローンしたら——コマンドは後述——`regex/` ディレクトリで `make repl` を実行するとこうなります)。

```repl
Main> :module Regex
Imported module Regex
Main> :exec printLn (test "colou?r" "my favourite colour")
Right True
Main> :exec printLn (test "gr[ae]y" "a green wall")
Right False
```

本物のパターン構文が入力され、自作のパーサでパースされ、先ほどの 1 行でマッチされる。(`Right` というラッパーは、パターン自体が正しい形だったというエンジンからの報告です——この物語は[公開 API](./15-public-api.md) で語られます。)

これが本書全体を貫くパターンです。高度に聞こえるもの——微分ベースのマッチング、パーサコンビネータ、機械検証された証明——は、言語が問題にフィットしていれば、小さなものだと分かります。関数型プログラミングの要点は知的な洗練ではありません。コードが*短くなると同時に、信頼できるようになる*ことです。

## なぜ Haskell ではなく Idris 2?

関数型プログラミングの入門先として、まず名前が挙がるのはたぶん Haskell です。なので Idris 2 を選ぶ理由は先に説明しておきます。Idris は Haskell ファミリーの関数型言語で、Haskell を見たことがあれば構文はかなり見覚えのあるものに映るはずです。ただ、いくつかの点で Haskell とは違う選択をしていて、*最初の*関数型言語としては、その選択がどれも学ぶ側に有利に働きます。

**Idris は正格(strict)であり、遅延(lazy)ではありません。** Haskell では式は遅延評価されます——書いた時点ではなく、いつか何かがその値を要求した時点で評価されるのです。遅延評価は強力ですが、*いつ*処理が走り、*どれだけメモリを使うか*についての直感をゼロから作り直す必要があり、その作り直しこそが Haskell の最も急な学習曲線のひとつです。

Idris は Python や JavaScript や Rust と同じく先行評価です。引数が計算されてから、関数が走る。プログラムの性能に関するあなたの既存のメンタルモデルは、ほぼそのまま持ち越せます。(Haskell 勢へ:そう、デフォルトでは遅延無限リストもない、という意味でもあります——Idris には明示的な `Inf` 型がありますが、本書では必要ありません。)

**やり方は、たいてい明白なものが 1 つだけあります。** Haskell は、数十年分の拡張、複数の文字列型、そして何をするにも 5 つのライブラリがそろった、栄光ある巨大言語です。Idris 2 は小さく新しい言語なので、道はよく照らされています。文字列型は 1 つ、`point.x` のようなドットアクセスが最初から付いてくるレコード構文が 1 つ、do 記法もインターフェースも初日から組み込み。選ぶ時間が減り、作る時間が増えます。

**ホール(hole)がコンパイラをペアプログラマにします。** Idris では、プログラムに穴——`?` で始まる名前——を開けたまま書くことができ、コンパイラはそこに収まるべきものの型と、それを組み立てるために手元にあるものすべてを、正確に教えてくれます。

コードを書いてから型チェッカーと口論するのではなく、型チェッカーと会話するのです。このワークフローは、型付き言語が持つオンボーディング機能として単独で最高のものであり、[速習コース](./04-idris-crash-course.md)で主役を演じます。

**全域性(totality)チェッカーが誠実さを教えてくれます。** Idris は、関数が*全域(total)*であること——起こりうるすべての入力を処理し、必ず停止すること——を検査できます。本書ではこれをエンジン全体で有効にします。アカデミックに聞こえますが、実際には、忘れていた `case` や終わらない再帰をコンパイル時に捕まえてくれる、疲れを知らないレビュアーです。さらに終盤の章では、これこそが[テストを定理に変える](./18-proofs.md)ための鍵だったと、静かに判明します。

そして、この選択を安全にしてくれるのが次の事実です。**本書で学ぶことは、すべて Haskell に一対一で対応します。** 代数的データ型、パターンマッチ、高階関数、インターフェース(Haskell では型クラスと呼びます)、モノイド、ファンクタ、do 記法、パーサコンビネータ——すべてそのまま移り、大半は同一かほぼ同一の構文です。

これは意図的です。あなたはメインストリーム言語の代わりにブティック言語を学ぶのではありません。ML ファミリー全体に共通する核を、その一番フレンドリーなメンバーを通して学ぶのです。[最終章](./21-whats-next.md)には、飛び移りたくなったときのための、Idris から Haskell への明示的な対応表があります。

> [!NOTE]
> Idris の一番の有名どころは*依存型(dependent types)*——値に依存できる型で、プログラムについての証明を可能にします——です。本書でも終盤で本物の依存型をひと口味わいますが、それはデザートであって、メインディッシュではありません。読み進めるのに依存型の知識は要りませんし、知っているふりを求めることもしません。

## 数学は必要?

いいえ——そして、なぜ不要なのかをきちんと述べておく価値があります。理論ファーストの教え方が植え付けたのが、まさにこの恐怖だからです。

数学の血筋を持つ言葉には、いくつか出会うことになります。*モノイド*は、私たちのエンジンの中に 2 つ潜んでいたと判明したときに登場しますし、マッチングアルゴリズムの名前は文字通り*微分(derivative)*です。しかしどの場合も、言葉はコードの*後*にやって来ます。すでに作ってテストし終えたものに、名前が付くだけです。自分が作ったものに立派な名前があったと知るのは、名前を理解するまで作ってはいけないと言われるより、ずっと良い気分です。

そして例の「モ」で始まる言葉について。本書にモナドのチュートリアルはありません。do 記法は、作用を順に並べる必要が生じたときに登場し、誠実に使われ、その仕組みは私たち自身のパーサのコードがそのパターンを目に見える形にしたまさにそのとき——[パーサコンビネータ](./13-parser-combinators.md)のあたり——に説明されます。ブリトーは一切登場しません。

## 作らないもの

スコープについて、最初に正直に。私たちのエンジンは本物のパターン——クラス、エスケープ、選択、繰り返し、回数指定——にマッチしますが、あくまで*マッチャー*であり、完全な PCRE クローンではありません。具体的には、次のものは作りません。

- **キャプチャグループ**——丸括弧のグループがマッチした部分文字列の抽出。私たちの丸括弧はグループ化しますが、キャプチャはしません。
- **アンカー**(`^` や `$`)——私たちの `match` は定義からして文字列全体のマッチであり、文字列内の検索用には `contains` を作ります。
- **後方参照**(`(\w+) \1` のような)——これらはそもそも正規言語ではなく、まさにエンジンをバックトラッキングへ追い込む張本人です。
- **Unicode 文字カテゴリ**(`\p{Greek}` のような)——私たちの文字集合は範囲と否定を扱え、アイデアを学ぶにはそれで十分です。
- **RE2 流の最適化 DFA コンパイラ**——私たちのエンジンはそれなしで線形時間です。ささやかな定数倍のコストと引き換えに。

どれも、不可能だから省くわけではありません——大半は[この先へ](./21-whats-next.md)にスケッチ付きの演習として再登場します。省くのは、本書のすべての章が関数型プログラミングを教えるために存在するからです。これらの機能は、レッスンというより正規表現の話になってしまうのです。

## コミット履歴こそが本書

始める前にもうひとつだけ。この先のすべての読み方を形作る話です。

本書は、書かれてから実装されたのではありません。*コミットされた*のです。コードを作るすべての章は、リポジトリの実際のコミットに対応しています。まず失敗するテストを追加するコミット(`(red)` と記されます)、続いてそれを通す最小の実装のコミット(`(green)`)。物語の中盤にある実際のペアを、`git log` が表示するとおりの姿でどうぞ。

```
d1a0950 test(core): specs for matches, end to end (red)
d8e7c5c feat(core): matches — fold deriv, then ask nullable (green)
```

履歴こそがチュートリアルです。どのコミットをチェックアウトしても、あなたは本書のとある一文の場所に正確に立っていて、コードは本文が説明するとおりの状態になっています。

いま手に入れておきましょう。

```sh
git clone https://github.com/ubugeeei-prod/lets-start-functional.git
```

`regex/` ディレクトリがエンジンで、`content/` がいま読んでいる本文です。中で `git log --oneline` を実行すれば、物語全体が一番下の最古のコミットから順に並んでいるのが見えます。scaffold、red、green、red、green……そして自作エンジンの上に築かれた、動くレキサまで。

コミットを再生しながら読み進める必要はありません——必要なコードはすべて本文が引用します——が、履歴がそこにあると知ることは、本書との契約を変えます。本書に擬似コードは 1 行もありません。すべては実際に動いたものであり、動くところをあなたも見られるのです。

## まとめ

- 関数型プログラミングの評判の問題は、動機より先に抽象を教えることから来ています。本書はそれを逆転させ、ひとつの本物のプロジェクトの中で、各機能に存在価値を証明させます。
- そのプロジェクトが正規表現エンジンです。なじみのある問題で、木の上の純粋な関数だけで完結する領域で、そして設計そのものによって打ち倒せる現実世界の悪役(壊滅的バックトラッキング)がいます。
- 完成したエンジンのマッチングアルゴリズムは、2 つの小さな補助関数の上の 1 行のコードです——正しい土台があれば難しいことは小さくなる、という本書で繰り返されるレッスンの予告編です。
- Idris 2 を使うのは、正格で(性能の直感がそのまま生きる)、小さく(やり方が明白)、対話的で(ホールがコンパイラを協力者に変える)、誠実(全域性チェッカー)だからです。しかも学んだことはすべて Haskell に一対一で移り、最終章がその対応表を明示します。
- 作るのはマッチャーであって PCRE クローンではありません。キャプチャグループ、アンカー、後方参照、Unicode カテゴリ、DFA コンパイルはなし——それらをどう作るかは[この先へ](./21-whats-next.md)を参照してください。
- リポジトリのコミット履歴こそが本書です。red のテストコミットと green の実装コミットが、どのステップでも再生可能な形で並んでいます。

次はいよいよ、悪役との正式なご対面です。正規表現エンジンとは実際のところ何なのか、主流のエンジンはどう爆発しうるのか、そして私たちのエンジンを安全に保つ 1964 年の忘れられたアイデアとは——[正規表現エンジンとは](./02-regex-engines.md)へ。
